3. Gates before connecting to real backends

Gate A: foundation (before connecting any client to the API; about 3–4 weeks)

  • S-01 Extract packages/domain and move the existing tests over
  • Introduce the data-adapter interface in web, mobile and desktop (local now, remote later)
  • W-04 / W-01 Modularise the web app, delete overridden code, remove string-built HTML and inline handlers
  • W-02 / S-11 Visible save failures and central error reporting
  • S-07 / S-08 / S-09 Decide money (minor units), time (UTC + tenant zone) and id (UUIDv7) formats
  • S-02 Remove the client-side API key and add the login flow design

Gate B: platform readiness (before any beta)

  • M-01 / M-02 Upgrade Expo/React Native, install, commit the lockfile, run on iPhone and Android
  • M-03 / M-05 / M-08 Keyboard handling, error boundary, safe-area context
  • D-01 / D-04 / D-05 / D-07 Upgrade Electron and builder, file recovery, icons, signing, updater, permission and fuse hardening
  • D-10 Run the desktop app on Windows, macOS and Linux

Gate C: release readiness (before production)

  • W-03 / M-04 / H-02 Accessibility fixes and audits (axe plus screen readers)
  • D-02 / D-03 Strict CSP and encryption at rest
  • W-10 / D-10 Real browser, device and Electron end-to-end tests
  • M-10 / H-01 / H-03 Store requirements, verified marketing claims, production forms

5. Findings in detail

Blocker: fix before connecting to a backend or releasing. High: before beta. Medium: before production. Low: polish. Effort is a rough estimate for one engineer. Click a finding to expand it.


BlockerSharedS-01 Business rules are triplicated with no single source of truth
Finding
The web app, the mobile engine (generated from the web code by a script) and the desktop renderer each carry their own copy of validation, stock effects, workflows and the scheduler. The old and new versions of several web functions also coexist (see W-04).
Impact
Every fix must be made three times; behaviour will drift between platforms and from the future server.
Recommendation
Extract one packages/domain (TypeScript) first; make web, mobile, desktop and the API import it. Reuse the existing ~100 checks as golden tests.
Effort · evidence
Large (1–3 weeks) · Code review
BlockerSharedS-02 No authentication, authorization or multi-user model
Finding
There is no login. Roles in Team & Users are labels only and nothing is enforced. An API key is generated and shown in the browser.
Impact
Anyone with the device can read and change everything. Not acceptable for an enterprise product or any backend connection.
Recommendation
Backend-issued sessions (OIDC/PKCE), RBAC and tenant isolation. Remove the client-side API key UI; keys are created and shown once by the server.
Effort · evidence
Large (1–3 weeks) · Code review
HighSharedS-03 Rules that must be enforceable are enforced only in the client
Finding
Plan seat limits, SMS opt-out compliance, SKU/email uniqueness, stock integrity and SLA timers all run in the browser or app. Editing localStorage or the data file bypasses them.
Impact
Plan limits, compliance and integrity can be bypassed.
Recommendation
Move them to the server (transactions, constraints, entitlement and compliance services); keep client copies for fast feedback only.
Effort · evidence
Large (1–3 weeks) · Code review
HighSharedS-04 Whole-state persistence with no versioning or conflict control
Finding
Every change serialises the entire state object; two tabs or devices overwrite each other (last write wins). Cross-tab sync replaces the whole state.
Impact
Silent loss of edits when two sessions are open; cost grows with data size.
Recommendation
Per-record storage with version and updated_at; sync protocol with conflict handling (see backend plan §9).
Effort · evidence
Medium (2–5 days) · Code review
HighSharedS-05 Hard capacity ceiling from browser and device storage
Finding
Measured about 123 KB per 1,000 records (20,000 records = 2.4 MB). localStorage is about 5 MB (roughly 40,000 records); Android AsyncStorage is commonly limited to about 2 MB per value (roughly 17,000 records). Verify on device.
Impact
Data silently stops saving or fails to load past the ceiling.
Recommendation
SQLite on native clients, server as source of truth, local cache with eviction.
Effort · evidence
Medium (2–5 days) · Tested (Node/jsdom)
MediumSharedS-06 Metrics and results are simulated but presented as real
Finding
Email open rates, SMS click rates, social reach and campaign counts come from random numbers; ‘Send’ and ‘Publish’ do not contact any provider. The SMS page says quiet hours are respected, but nothing enforces them.
Impact
Misleading in a business tool; a compliance risk if users believe messages were sent.
Recommendation
Label simulated data clearly (or hide the actions) until real providers are connected; enforce quiet hours on the server.
Effort · evidence
Small (≤1 day) · Code review

Impact

HighWebW-01 Script injection through restored backups
Finding
Verified: a backup whose order id is ‘'+(window.__xss=1)+'’ executes code when the row button is clicked. Record ids and keys are placed unescaped inside inline onclick attributes. Text fields are escaped correctly (tested).
Impact
Self-XSS today; becomes a real attack once data comes from a server or other users. In the desktop app the injected code could call the native bridge.
Recommendation
Stop building HTML with string templates and inline handlers; use a framework or addEventListener with data attributes. Validate every restored or synced record.
Effort · evidence

HighWebW-02 Silent data loss when storage fails

Impact

Recommendation

6. What is solid

  • Schema-driven modules: one definition drives lists, forms, validation and actions, which makes the move to an API straightforward.
  • The business rules (stock effects, workflows, compliance wording, SLA, plan limits) are explicit and covered by about 100 automated checks.
  • Offline-first behaviour and local persistence work as designed (apart from the failure cases above).
  • Electron shell follows the right security shape: sandbox, context isolation, validated IPC, blocked navigation, external links in the browser.
  • React Native renders text safely by default, so mobile has no equivalent of the web injection issue.
  • Consistent brand system built from the supplied logo, light and dark themes, and a clear information architecture.
  • The backend plan (v2) already anticipates most gaps: shared domain package, sync, public API, entitlements.

7. Method, limits and evidence

Method

  • Static analysis: ESLint (recommended rules) on the web and homepage scripts, mobile engine, desktop main, preload and bridge code. JSX false positives (no React plugin) were discarded.
  • Accessibility: axe-core on the dashboard, orders list, add-order form and homepage (colour contrast excluded).
  • Behaviour probes: Scripted tests for script injection, storage failure, stock reversal, currency, date handling, modal keyboard handling and scale (1k, 5k and 20k records).
  • Dependency check: npm registry versions for Expo, React Native, Electron and electron-builder, plus Expo SDK 52’s bundled module list.
  • Code review: Manual review of all three codebases and the homepage against enterprise expectations: security, data integrity, accessibility, release and operations.

Limits of this review

  • No real browsers, phones, emulators or Electron runtime were available; web, desktop and homepage were exercised in a simulated DOM (jsdom) and the Electron main process through a mock.
  • Colour contrast, real-device layout, touch behaviour and screen-reader behaviour could not be tested and are likely to produce further findings.
  • Performance numbers come from Node/jsdom and are indicative only.
  • Store and platform policy deadlines change often; items marked ‘verify’ should be re-checked against current Google Play, Apple and Electron release policies.
